= InfoSec Sidecar

This workshop builds the InfoSec sidecar pattern end to end: an application outside the mesh, holding a SPIFFE X.509 identity from its own SPIRE server, calls a service on Red Hat OpenShift Service Mesh 3 over mTLS that the ingress gateway passes through untouched.
By the end you can stand up the identity plane with Zero Trust Workload Identity Manager, federate it with an external trust domain, route a TLS session through the gateway on SNI alone, and prove with Envoy's own logs that the mesh workload saw the caller's real SPIFFE ID.

Before you start, make sure your environment meets the xref:setup-requirements.adoc[Setup Requirements].

== What You Build

image::infosec-sidecar-flow.svg[InfoSec sidecar flow,720]

Solid arrows are one TLS session: it starts in the InfoSec sidecar next to the external application and ends in the `istio-proxy` of the mesh workload.
Dashed arrows are the identity plane that hands out SVIDs and trust bundles.
The ingress gateway sits on the data path but never holds a key for it.
