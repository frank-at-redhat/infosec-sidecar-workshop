= InfoSec Sidecar: Setup Requirements

This page lists everything needed to run the InfoSec Sidecar workshop.
The instructor prepares the cluster and accounts ahead of time; attendees prepare their workstations.

== Cluster

[cols="1,3",options="header"]
|===
|Item |Requirement

|Platform
|OpenShift Container Platform 4.21 or later, on any platform.
Validated on bare metal and vSphere.
A disconnected cluster works once the images below are mirrored.

|Size
|One cluster per attendee or pair.
Three worker nodes with 4 vCPU and 16 GiB each is enough; the workshop's own footprint is under 2 vCPU and 4 GiB.

|Storage
|A default `StorageClass` that can bind a 5 GiB `ReadWriteOnce` claim for the SPIRE server.

|Ingress
|The default OpenShift router.
Module 3 exposes the mesh gateway with a passthrough `Route`; MetalLB is an alternative shown in a tab, not a requirement.
|===

== Operators and Cluster Components

[cols="1,1,2",options="header"]
|===
|Component |Installed by |Used in

|Zero Trust Workload Identity Manager 1.0 or later (`zero-trust-workload-identity-manager`, channel `stable`)
|The attendee, in Module 1
|Modules 1 to 6

|Red Hat OpenShift Service Mesh 3.4 or later (`servicemeshoperator3`, channel `stable`)
|The attendee, in Module 2
|Modules 2 to 6

|Istio `Gateway` and `VirtualService` CRDs (`networking.istio.io`)
|The Service Mesh Operator, in Module 2.
Gateway API is not used: OpenShift's Ingress Operator owns those CRDs and does not ship `TLSRoute`; Module 3 explains.
|Module 3

|Kiali (optional)
|The instructor, if wanted for the walkthrough
|Module 6, to show the external caller
|===

====
Service Mesh using SPIRE through Zero Trust Workload Identity Manager as its certificate authority is a Technology Preview feature in OpenShift Service Mesh 3.4.
Say so when you deliver the workshop to a customer, and check the current release notes for the status.
====

== Attendee Accounts, Projects and Roles

Every attendee needs `cluster-admin` on their cluster: the workshop installs two Operators, and creates cluster-scoped `ClusterFederatedTrustDomain` and `ClusterSPIFFEID` resources.

== Network and Image Access

The cluster pulls these images.
Mirror them for a disconnected cluster; `images-mirror.txt` in the release lists them in a form `oc mirror` accepts.

[cols="2,2",options="header"]
|===
|Image |Used for

|`registry.redhat.io/zero-trust-workload-identity-manager/*`
|The Operator and its SPIRE operands

|`registry.redhat.io/openshift-service-mesh/*`
|The Operator, `istiod`, the sidecar and gateway proxy

|`ghcr.io/spiffe/spire-server:1.13.3`
|The external trust domain's SPIRE server (Module 4)

|`ghcr.io/spiffe/spire-agent:1.13.3`
|The SPIRE agent inside the InfoSec sidecar (Module 6)

|`docker.io/envoyproxy/envoy:v1.33.0`
|The Envoy inside the InfoSec sidecar (Module 6)

|`registry.access.redhat.com/ubi9/httpd-24`
|The `payments` sample workload (Module 2)
|===

Workstations need to reach the cluster API and the cluster's `*.apps` domain.
Nothing in the workshop needs the internet from the cluster once the images are available.

== Verification Checklist

Each attendee runs these before the workshop starts.

. Check that you are logged in to the cluster as a cluster administrator:
+
[source,bash,role=execute]
----
oc auth can-i create clusterfederatedtrustdomains
----
+
It prints `yes`.

. Check that a default storage class exists:
+
[source,bash,role=execute]
----
oc get storageclass
----
+
One class is marked `(default)`.

. Check the cluster version:
+
[source,bash,role=execute]
----
oc get clusterversion version \
  --output jsonpath='{.status.desired.version}{"\n"}'
----
+
It prints `4.21` or later.

. Check that `istioctl` is installed:
+
[source,bash,role=execute]
----
istioctl version --remote=false
----
+
It prints a client version.
