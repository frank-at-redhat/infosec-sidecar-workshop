= Ingress Passthrough

Expose `payments` through an Istio ingress gateway whose TLS server passes sessions through on SNI without terminating them.
After this module an outside caller can reach the `payments` sidecar's own TLS listener, which is what makes end-to-end identity possible in Module 6.

[#why-istio-gateway]
== Why the Istio Gateway and Not Gateway API

Service Mesh 3 supports both the Kubernetes Gateway API and Istio's own `Gateway` and `VirtualService` resources.
This workshop uses Istio's, and the reason is an OpenShift constraint worth knowing before a customer asks.

Routing raw TLS on SNI with Gateway API needs the `TLSRoute` resource, which is still in the Gateway API experimental channel.
Since OpenShift 4.19 the Ingress Operator owns every CRD in the `gateway.networking.k8s.io` group and installs only the standard channel: `GatewayClass`, `Gateway`, `HTTPRoute`, `GRPCRoute` and `ReferenceGrant`.
A `ValidatingAdmissionPolicy` named `openshift-ingress-operator-gatewayapi-crd-admission` rejects any attempt by anyone other than the operator to create or change a CRD in that group, so `TLSRoute` cannot be added:

----
Gateway API Custom Resource Definitions are managed by the Ingress
Operator and may not be modified
----

Istio's `Gateway` with `tls.mode: PASSTHROUGH` does the same SNI routing, lives in the `networking.istio.io` group that Service Mesh owns, and is fully supported.
The trade-off is small: nothing creates the gateway pod for you, so Exercise 1 declares it, and the approval gate moves from a namespace selector to the `hosts` entry on the `Gateway`.
If `TLSRoute` reaches the standard channel and OpenShift ships it, the Gateway API form is a drop-in replacement.

[NOTE]
====
Impersonating the Ingress Operator's service account gets past the policy, and you may see that suggested online.
Don't put it in front of a customer: it is unsupported, and the cluster will flag the foreign CRD at the next minor upgrade.
====

[#exercise-1]
== Exercise 1: Create the Gateway

. Create the gateway's pod and its Service.
The `inject.istio.io/templates: gateway` annotation makes Istio inject the pod as a gateway proxy rather than a sidecar, and the `istio: infosec-passthrough` label is what the `Gateway` resource selects:
+
[source,yaml]
----
include::example$gateway-deployment.yaml[]
----
+
[source,bash,role=execute]
----
oc apply -f $MANIFESTS/gateway-deployment.yaml
----

. Create the `Gateway`.
Two things to read in it: `mode: PASSTHROUGH`, which is the whole pattern, and the `payments/` prefix on the host, which is InfoSec's approval gate: only a `VirtualService` in the `payments` namespace may bind to that hostname.
+
[source,yaml]
----
include::example$gateway-passthrough.yaml[]
----
+
[source,bash,role=execute]
----
sed "s/APPS_DOMAIN/${APPS}/" $MANIFESTS/gateway-passthrough.yaml \
  | oc apply -f -
----

. Wait for the gateway pod:
+
[source,bash,role=execute]
----
oc rollout status deployment/infosec-passthrough \
  --namespace istio-ingress \
  --timeout 180s
----
+
It prints `deployment "infosec-passthrough" successfully rolled out`.

[#exercise-2]
== Exercise 2: Route on SNI

. Create the `VirtualService` in the `payments` namespace.
The app team owns this resource; the `sniHosts` entry is the name the external caller will send, and the destination is the workload's real port:
+
[source,yaml]
----
include::example$virtualservice-payments.yaml[]
----
+
[source,bash,role=execute]
----
sed "s/APPS_DOMAIN/${APPS}/g" $MANIFESTS/virtualservice-payments.yaml \
  | oc apply -f -
----

. Confirm the gateway is listening on SNI and forwarding as TCP:
+
[source,bash,role=execute]
----
istioctl proxy-config listener \
  deploy/infosec-passthrough \
  --namespace istio-ingress \
  --port 8443 \
  --output json \
  | jq -r '.[].filterChains[]
      | "\(.filterChainMatch.serverNames) -> \(.filters[0].name)"'
----
+
It prints your `payments` hostname followed by `envoy.filters.network.tcp_proxy`.
No `http_connection_manager` and no TLS transport socket: the gateway reads the SNI and copies bytes.

[#exercise-3]
== Exercise 3: Expose the Gateway

Pick the tab that matches your cluster.
The `Route` works on every cluster; MetalLB is what a bare-metal production deployment would use.

[tabs]
====
OpenShift Route::
+
--
. Create a passthrough `Route` to the gateway Service.
The router forwards on SNI and never decrypts, so it adds a hop but no key:
+
[source,yaml]
----
include::example$route-gateway.yaml[]
----
+
[source,bash,role=execute]
----
sed "s/APPS_DOMAIN/${APPS}/" $MANIFESTS/route-gateway.yaml \
  | oc apply -f -
----

. Save the host for later modules:
+
[source,bash,role=execute]
----
export GW_HOST=payments.${APPS}
export GW_ADDR=${GW_HOST}
echo $GW_HOST
----
--
MetalLB::
+
--
. Create an `IPAddressPool` named `mesh-ingress` with the MetalLB Operator, then replace the gateway Service with the `LoadBalancer` variant:
+
[source,yaml]
----
include::example$gateway-metallb.yaml[]
----
+
[source,bash,role=execute]
----
oc apply -f $MANIFESTS/gateway-metallb.yaml
----

. Read the VIP and save it.
Use a hostname your DNS or `/etc/hosts` maps to the VIP, and change the host in the `Gateway` and `VirtualService` to match:
+
[source,bash,role=execute]
----
export GW_ADDR=$(oc get service infosec-passthrough \
  --namespace istio-ingress \
  --output jsonpath='{.status.loadBalancer.ingress[0].ip}')
export GW_HOST=payments.mesh.example
echo $GW_ADDR
----
--
====

. Make a TLS connection through it and look at the certificate that comes back:
+
[source,bash,role=execute]
----
openssl s_client -connect ${GW_ADDR}:443 \
  -servername ${GW_HOST} \
  -alpn istio </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer -ext subjectAltName
----
+
The issuer is `CN = Mesh SPIRE CA` and the SAN is `URI:spiffe://cluster.local/ns/payments/sa/payments`.
That certificate belongs to the `payments` sidecar, two hops away.
Neither the router nor the gateway substituted its own, which is the proof that nothing on the path terminated TLS.
The handshake itself fails right after, because you presented no client certificate and the namespace is `STRICT`; Module 6 fixes that.
